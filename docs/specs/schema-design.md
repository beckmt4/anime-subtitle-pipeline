# SQLite Schema Design — Anime Subtitle Pipeline

**Status:** Implemented  
**Issue:** [#34 – Design SQLite schema for media assets, subtitle candidates, benchmark runs, and review tasks](https://github.com/beckmt4/anime-subtitle-pipeline/issues/34)  
**Related epic:** [#18 – Persistent state / artifact registry](https://github.com/beckmt4/anime-subtitle-pipeline/issues/18)

---

## 1. Why a schema before everything else

The current pipeline is file-driven: outputs land in `outbox/` and `logs/` as flat files.  That is fine for one-off runs but breaks down when you need:

- reproducible benchmark history that survives re-runs
- accepted vs. rejected candidate tracking
- a review queue with auditable decisions
- retry / resume / reprocess behaviour
- library-scale processing where the same media file should not be re-processed

Without an explicit schema you accumulate ad-hoc JSON files in incompatible formats.  Writing the schema first gives implementation issues a concrete reference and prevents drift.

## 2. Table map and rationale

```
media_assets
  └─ stream_assets           (audio, subtitle, video streams inside a container)

subtitle_candidates          (every subtitle variant produced or derived)
  │   parent_candidate_id ──► subtitle_candidates (lineage: asr → mt → mt_llm)
  ├─ benchmark_runs          (one run compares ref vs. hyp)
  │     └─ benchmark_comparisons  (per-metric rows for a run)
  ├─ review_tasks            (human review decision for a candidate)
  │     └─ review_task_candidates  (join — one task may cover multiple candidates)
  ├─ artifacts               (versioned output files, e.g. .srt, .ass)
  └─ state_transitions       (audit log of every status change)
```

### 2.1 `media_assets`

**Why its own table:** A media file (`.mkv`, `.mp4`) is the root entity.  Everything else is derived from it.  Storing it separately lets `stream_assets` normalise the per-stream metadata, avoids repeating file metadata on every candidate row, and makes it easy to answer "what files have we processed?".

**Natural key:** `media_hash` (SHA-256 of the file content).  If the same file is seen under a different path, the hash collision triggers an upsert that updates the path, preserving the canonical identity.

### 2.2 `stream_assets`

**Why its own table:** A container has multiple streams (audio, subtitle, video) and each has independent metadata (codec, language, title, index).  Embedding this on `media_assets` would require a JSON blob and lose queryability.

**FK:** `media_asset_id → media_assets(id) ON DELETE CASCADE` — if the media record is deleted, all its stream metadata goes with it.

### 2.3 `subtitle_candidates`

**Why its own table:** The core entity.  Every subtitle variant — whether produced by ASR, extracted from an embedded stream, translated by an MT engine, or polished by an LLM — is a candidate.  Keeping all variants in one table with a `source` discriminator column enables comparisons across sources for the same `media_hash`.

**Lineage (`parent_candidate_id`):** A self-referential FK.  An ASR candidate has `parent_candidate_id = NULL`.  The MT translation derived from it stores the ASR candidate's `id` as its parent.  An LLM-polished version of the MT output stores the MT candidate's `id`.  This single column enables full lineage traversal (`SELECT … WHERE parent_candidate_id = ?`) without additional tables.

**Status enum:** `pending | accepted | failed | review_required`.  All transitions are recorded in `state_transitions`.

### 2.4 `benchmark_runs`

**Why its own table:** A benchmark run is a snapshot comparison of a reference candidate against a hypothesis candidate at a point in time.  Separating it from `subtitle_candidates` keeps the candidates table focused on content and lets you store multiple benchmark runs against the same pair of candidates.

**Convenience columns (`wer`, `bleu`, `chrf`):** Denormalised copies of the top-level metrics for fast sorting/filtering without parsing `metrics_json`.

**FK to candidates:** `reference_candidate_id` and `hypothesis_candidate_id` are nullable FKs to `subtitle_candidates`.  Nullable because a benchmark might compare against an external reference file that was not generated by this pipeline.

### 2.5 `benchmark_comparisons`

**Why its own table:** `benchmark_runs` stores aggregate metrics in a JSON blob.  `benchmark_comparisons` normalises one row per (run × metric), which allows:

- querying "what was the WER for every run on media hash X?" without JSON parsing in SQL
- linking each comparison row back to the exact reference and hypothesis candidate pair
- storing arbitrary future metrics without schema changes

**FK:** `benchmark_run_id → benchmark_runs(id) ON DELETE CASCADE` — comparisons are children of a run.

### 2.6 `review_tasks`

**Why its own table:** A review task is a decision (approve / reject / reprocess) made by a human reviewer, separate from the candidate's current status.  Keeping it separate lets multiple review cycles happen on the same candidate and allows the queue to be queried independently.

**Primary candidate (`candidate_id`):** The direct FK covers the common one-to-one case.  The `review_task_candidates` join table supports the less-common case where a reviewer wants to compare several variants side-by-side in a single task.

**Reprocess reason:** A free-text `reprocess_reason` column captures why a candidate was sent back rather than burying this in notes.

### 2.7 `review_task_candidates`

**Why its own table:** Pure join table — `(review_task_id, candidate_id)` composite primary key.  Allows a single review task to reference multiple candidates (e.g. "compare ASR-only vs MT-polished before deciding which to accept") without changing the `review_tasks` structure.

### 2.8 `artifacts`

**Why its own table:** An artifact is a concrete output file (`.srt`, `.ass`, `.vtt`) produced from a candidate.  Tracking it separately from the candidate enables:

- versioning (the same candidate may be reprocessed, producing v2 of the same artifact type)
- provenance (which file was sent to the user corresponds to which candidate)
- supersession (when a new version is produced, the old one is marked `superseded` rather than deleted)

**Version column:** An integer that increments per `(candidate_id, artifact_type)`.  Combined with `file_hash`, this gives a complete reprocess history.

**Status enum:** `active | superseded | deleted`.  Nothing is hard-deleted from this table by default.

### 2.9 `state_transitions`

**Why its own table:** A generic audit log for status changes on any entity.  Rather than one transition table per entity type, a single table with `(entity_type, entity_id)` discriminators covers candidates, review tasks, and artifacts.  This gives a complete processing timeline for any entity without denormalising every status onto the entity row.

**Fields:** `from_status` (NULL for the initial creation event), `to_status`, `reason`, `actor` (system component or user).

## 3. Status enumerations

### Candidate statuses

| Value            | Meaning                                                      |
|------------------|--------------------------------------------------------------|
| `pending`        | Produced but not yet evaluated.                              |
| `accepted`       | Passed quality checks and approved for delivery.             |
| `failed`         | Evaluation or processing error; not usable.                  |
| `review_required`| Quality gate flagged it; needs human review before accept.   |

### Review task statuses

| Value       | Meaning                                                             |
|-------------|---------------------------------------------------------------------|
| `pending`   | Task created; reviewer has not yet acted.                           |
| `approved`  | Reviewer accepted the candidate(s).                                 |
| `rejected`  | Reviewer rejected the candidate(s).                                 |
| `reprocess` | Reviewer sent the candidate(s) back for re-processing; see `reprocess_reason`. |

### Artifact statuses

| Value        | Meaning                                                         |
|--------------|-----------------------------------------------------------------|
| `active`     | Current authoritative output file.                              |
| `superseded` | Replaced by a newer version; kept for history.                  |
| `deleted`    | Marked as removed (soft delete).                                |

---

## 4. Artifact versioning approach

When a candidate is reprocessed and a new output file is produced:

1. All existing `artifacts` rows for `(candidate_id, artifact_type)` with `status = 'active'` are updated to `status = 'superseded'`.
2. A new `artifacts` row is inserted with `version = max(version) + 1` and `status = 'active'`.

This approach preserves the full reprocess history (enabling rollback or audit) without requiring a separate version-history table.

## 5. Candidate lineage

The `parent_candidate_id` self-FK on `subtitle_candidates` is the sole mechanism for lineage.  A typical chain:

```
subtitle_candidates id=1  source='asr'    parent=NULL       (Whisper output)
subtitle_candidates id=2  source='mt'     parent=1          (Helsinki-NLP MT)
subtitle_candidates id=3  source='mt_llm' parent=2          (GPT-4o polish)
```

To trace the full lineage of candidate 3:

```sql
-- Recursive CTE (SQLite supports WITH RECURSIVE since 3.8.3)
WITH RECURSIVE lineage(id, parent_candidate_id, source, source_id) AS (
    SELECT id, parent_candidate_id, source, source_id
    FROM subtitle_candidates WHERE id = 3
    UNION ALL
    SELECT c.id, c.parent_candidate_id, c.source, c.source_id
    FROM subtitle_candidates c
    JOIN lineage l ON c.id = l.parent_candidate_id
)
SELECT * FROM lineage ORDER BY id ASC;
```

The Python helper `ProcessingLedger.candidate_lineage(candidate_id)` performs this traversal iteratively and returns the chain root-first.

## 6. Minimum indexes

| Index name                        | Table                   | Columns                                  | Rationale                                                                    |
|-----------------------------------|-------------------------|------------------------------------------|------------------------------------------------------------------------------|
| `idx_media_assets_hash`           | `media_assets`          | `(media_hash)`                           | Natural-key lookup; all candidate inserts resolve the media asset this way.  |
| `idx_stream_assets_media`         | `stream_assets`         | `(media_asset_id)`                       | List streams for a given media asset.                                        |
| `idx_candidates_media`            | `subtitle_candidates`   | `(media_hash)`                           | Core queue query: "all candidates for this file".                            |
| `idx_candidates_parent`           | `subtitle_candidates`   | `(parent_candidate_id)`                  | Forward lineage traversal: "all children of this candidate".                 |
| `idx_candidates_source`           | `subtitle_candidates`   | `(source_id, model_version)`             | Deduplication: "has this source/model already produced a candidate?".        |
| `idx_candidates_status`           | `subtitle_candidates`   | `(status)`                               | Queue query: "all pending/review_required candidates".                       |
| `idx_benchmark_media`             | `benchmark_runs`        | `(media_hash)`                           | Benchmark history for a file.                                                |
| `idx_benchmark_comparisons_run`   | `benchmark_comparisons` | `(benchmark_run_id)`                     | List all per-metric rows for a run.                                          |
| `idx_benchmark_comparisons_ref`   | `benchmark_comparisons` | `(reference_candidate_id)`               | "All benchmark rows that used candidate X as reference".                     |
| `idx_benchmark_comparisons_hyp`   | `benchmark_comparisons` | `(hypothesis_candidate_id)`              | "All benchmark rows that used candidate X as hypothesis".                    |
| `idx_review_tasks_candidate`      | `review_tasks`          | `(candidate_id)`                         | "Does this candidate have an open review task?".                             |
| `idx_review_tasks_status`         | `review_tasks`          | `(status)`                               | Review queue query: "all pending tasks".                                     |
| `idx_artifacts_candidate`         | `artifacts`             | `(candidate_id)`                         | List all artifact files for a candidate.                                     |
| `idx_artifacts_media`             | `artifacts`             | `(media_hash)`                           | "All artifacts produced for this file".                                      |
| `idx_artifacts_status`            | `artifacts`             | `(status)`                               | Filter active vs. superseded artifacts.                                      |
| `idx_state_transitions_entity`    | `state_transitions`     | `(entity_type, entity_id)`               | Full transition history for any entity.                                      |
| `idx_state_transitions_created`   | `state_transitions`     | `(created_at)`                           | Time-range queries over the audit log.                                       |

## 7. Mapping from current file outputs to future persisted records

| Current output file                          | Future persisted record                                            |
|----------------------------------------------|--------------------------------------------------------------------|
| `outbox/<hash>_asr_ja.srt`                   | `subtitle_candidates` row with `source='asr'`; `artifacts` row with `artifact_type='srt'` |
| `outbox/<hash>_mt_en.srt`                    | `subtitle_candidates` row with `source='mt'`, `parent_candidate_id=<asr_id>`; `artifacts` row |
| `outbox/<hash>_mt_llm_en.srt`                | `subtitle_candidates` row with `source='mt_llm'`, `parent_candidate_id=<mt_id>`; `artifacts` row |
| `logs/benchmark_<run_id>.json`               | `benchmark_runs` row; `benchmark_comparisons` rows (one per metric) |
| `logs/comparison_<hash>.json`                | `benchmark_comparisons` rows linked to `benchmark_runs`           |
| Manual review decision (currently no record) | `review_tasks` row; `state_transitions` row recording the decision |
| In-memory candidate object                   | `subtitle_candidates` row                                          |
| `config.yaml` media path                     | `media_assets` row; `stream_assets` rows (one per ffprobe stream) |

## 8. Implementation notes

- All timestamps are stored as `TEXT` in ISO-8601 format (`datetime('now')` in SQLite).  This avoids timezone ambiguity and is human-readable.
- `segments_json` and `meta_json` use `DEFAULT '[]'` / `DEFAULT '{}'` so `json_each()` queries work without NULL guards.
- `PRAGMA foreign_keys = ON` is set on every connection.  All FKs are enforced at the application level by `init_db`.
- `PRAGMA journal_mode = WAL` enables concurrent reads while a write is in progress.
- The schema is applied with `CREATE TABLE IF NOT EXISTS` so `init_db` is safe to call on an existing database.  New columns on existing tables are added via `ALTER TABLE` migrations in `_MIGRATIONS` (applied idempotently).

## 9. Open questions / future work

- **Deduplication policy:** Should inserting a candidate with an identical `(media_hash, source_id, model_version)` raise an error, silently skip, or create a new version?  Currently each `store_candidate` call creates a new row.  A `UNIQUE` constraint on `(media_hash, source_id, model_version)` with an upsert policy is the likely next step.
- **Review task assignment:** The `review_tasks` table has no `assignee` column yet.  This will be needed when the review queue is implemented (#22).
- **Artifact storage backend:** `file_path` currently stores a local path.  A future `storage_backend` column (e.g. `local | s3`) and a `storage_uri` column would support remote storage.
- **Schema versioning:** A `schema_version` table (one row, monotonic integer) would allow migrations to be tracked and only applied once, replacing the current try/except approach.
